# 第一章：数据库基础概念

> 本章不涉及代码，旨在帮助没有数据库背景的嵌入式工程师建立对数据库的基本认知。

## 1.1 为什么需要数据库？

作为嵌入式开发工程师，你一定熟悉这些数据存储方式：

| 方式 | 典型场景 | 局限性 |
|------|----------|--------|
| 全局变量/结构体 | 运行时临时数据 | 掉电丢失 |
| 文件（文本/二进制） | 配置文件、日志 | 查询困难、并发冲突 |
| EEPROM/Flash 直写 | 少量关键参数 | 磨损、容量有限 |

当你的设备需要管理**大量结构化数据**时（如传感器历史记录、设备配置表、用户操作日志），上述方式会遇到以下问题：

1. **查询效率低**：从文件中查找满足特定条件的记录，需要逐行/逐字节扫描
2. **数据一致性差**：断电时写入了一半的数据，文件可能损坏
3. **并发访问困难**：多个线程/进程同时读写同一文件，容易出现竞态条件
4. **缺乏数据关系管理**：设备表与传感器表之间的关联关系难以维护

**数据库**就是为了系统性地解决这些问题而设计的软件。

## 1.2 什么是数据库？

数据库（Database）是一个**有组织地存储和管理数据的系统**。你可以把它想象成一个"智能的文件系统"：

- 普通文件系统：你需要自己管理数据格式、索引、并发、一致性
- 数据库：帮你处理这些底层细节，你只需要告诉它"存什么"和"查什么"

### 数据库的核心能力

```
┌─────────────────────────────────────────┐
│              数据库系统                    │
│                                         │
│  ┌─────────┐  ┌──────┐  ┌───────────┐  │
│  │ 结构化存储 │  │ 高效索引│  │ 事务与一致性│  │
│  └─────────┘  └──────┘  └───────────┘  │
│  ┌─────────┐  ┌──────┐  ┌───────────┐  │
│  │ 并发控制  │  │ 查询语言│  │ 数据安全   │  │
│  └─────────┘  └──────┘  └───────────┘  │
└─────────────────────────────────────────┘
```

## 1.3 关系型数据库

数据库有很多种类（键值数据库、文档数据库、图数据库等），其中最经典、最广泛使用的是**关系型数据库（Relational Database）**。

### 核心概念：表（Table）

关系型数据库用**表**来组织数据，就像 Excel 表格一样：

**devices 表（设备表）：**

| device_id | name       | type     | ip_address    |
|-----------|------------|----------|---------------|
| 1         | 温度传感器A | sensor   | 192.168.1.101 |
| 2         | 温度传感器B | sensor   | 192.168.1.102 |
| 3         | 网关设备    | gateway  | 192.168.1.1   |

**sensor_data 表（传感器数据表）：**

| id | device_id | temperature | humidity | timestamp           |
|----|-----------|-------------|----------|---------------------|
| 1  | 1         | 25.3        | 60.2     | 2024-01-01 10:00:00 |
| 2  | 1         | 25.5        | 59.8     | 2024-01-01 10:01:00 |
| 3  | 2         | 24.1        | 62.0     | 2024-01-01 10:00:00 |

### 关键术语

- **表（Table）**：数据的集合，类似结构体数组
- **行/记录（Row/Record）**：表中的一条数据，类似数组中的一个元素
- **列/字段（Column/Field）**：数据的属性，类似结构体的成员
- **主键（Primary Key）**：唯一标识一行记录的列，类似数组下标
- **外键（Foreign Key）**：引用另一个表主键的列，建立表与表之间的关系

### 用嵌入式思维理解

```c
// 嵌入式工程师熟悉的方式
struct Device {
    int device_id;      // 对应"列"
    char name[64];
    char type[32];
    char ip_address[16];
};

struct Device devices[100];  // 对应"表"
devices[0] = {1, "温度传感器A", "sensor", "192.168.1.101"};  // 对应"行"
```

**关系型数据库本质上就是把这种"结构体数组"的管理自动化了**，并提供了强大的查询、排序、过滤、关联能力。

## 1.4 SQL 语言简介

**SQL（Structured Query Language，结构化查询语言）** 是与关系型数据库交互的标准语言。

你可以把 SQL 理解为"对数据库下达指令的语言"，类似于 AT 指令之于 modem。

SQL 的四大基本操作（CRUD）：

| 操作 | SQL 语句 | 类比 |
|------|----------|------|
| 创建（Create） | `INSERT INTO` | 往数组添加元素 |
| 读取（Read）   | `SELECT` | 遍历数组查找数据 |
| 更新（Update） | `UPDATE` | 修改数组中某个元素 |
| 删除（Delete） | `DELETE` | 从数组中移除元素 |

示例（先有个印象，后续章节会详细讲解）：

```sql
-- 查询所有温度大于 25 度的记录
SELECT * FROM sensor_data WHERE temperature > 25.0;

-- 插入一条新的传感器数据
INSERT INTO sensor_data (device_id, temperature, humidity, timestamp)
VALUES (1, 26.1, 58.5, '2024-01-01 10:02:00');
```

## 1.5 数据库的类型

| 类型 | 代表产品 | 特点 | 嵌入式适用性 |
|------|----------|------|-------------|
| 大型关系型数据库 | Oracle, PostgreSQL | 功能完善、需要服务器 | ❌ 不适合 |
| 中型关系型数据库 | MySQL, MariaDB | C/S架构、需要独立进程 | △ 有限 |
| **嵌入式数据库** | **SQLite** | **零配置、单文件、进程内** | **✅ 非常适合** |
| 键值数据库 | LevelDB, Redis | 只有 key-value | △ 特定场景 |

**对于嵌入式系统，SQLite 几乎是唯一的最佳选择**，这就是我们接下来要深入学习的内容。

## 1.6 SQLite 内部实现原理

了解 SQLite 的内部实现，有助于你在嵌入式场景中做出更好的设计决策。

### 整体架构

SQLite 的内部实现可以分为以下几层：

```
┌───────────────────────────────────────────┐
│            SQL 接口层（API）                 │
├───────────────────────────────────────────┤
│         SQL 编译器（词法分析 → 语法分析）      │
│              ↓ 生成字节码                    │
├───────────────────────────────────────────┤
│         虚拟机（VDBE）── 执行字节码           │
├───────────────────────────────────────────┤
│         B-Tree 模块 ── 数据组织与索引         │
├───────────────────────────────────────────┤
│         Pager 模块 ── 页面缓存与事务          │
├───────────────────────────────────────────┤
│         OS 接口层（VFS）── 文件 I/O 抽象      │
└───────────────────────────────────────────┘
```

### B-Tree：数据的存储结构

SQLite 使用 **B-Tree（B树）** 作为核心数据结构来组织表和索引数据。

- **表数据**：存储在 B+Tree 中，叶子节点包含完整的行数据，以 `rowid` 为键排序
- **索引数据**：存储在 B-Tree 中，键是索引列的值，值是对应的 `rowid`

```
                    [  30  |  70  ]              ← 内部节点（只存键）
                   /       |       \
        [10|20|30]    [40|50|60|70]   [80|90]    ← 叶子节点（存实际数据）
```

**对嵌入式的意义**：B-Tree 保证了查询时间复杂度为 O(log N)，即使百万条记录，查找也只需约 20 次磁盘读取。

### 页面（Page）：磁盘 I/O 的基本单位

SQLite 将数据库文件划分为等大的 **页面（Page）**，默认大小为 **4096 字节**。

- 所有读写操作以页为单位进行
- B-Tree 的每个节点对应一个页面
- 页面大小可在创建数据库时配置（512 ~ 65536 字节）

```
数据库文件布局：
┌────────┬────────┬────────┬────────┬─────┐
│ Page 1 │ Page 2 │ Page 3 │ Page 4 │ ... │
│(文件头+ │(B-Tree │(B-Tree │(溢出页) │     │
│ 根节点) │ 内部页)│ 叶子页)│        │     │
└────────┴────────┴────────┴────────┴─────┘
```

**嵌入式优化建议**：将页面大小设置为与 Flash 扇区大小对齐（通常 4KB），可以减少写放大。

### Pager：缓存与事务管理

Pager 模块负责：

1. **页面缓存**：在内存中缓存常用页面，减少磁盘 I/O
2. **事务日志**：通过 **回滚日志（Rollback Journal）** 或 **WAL（Write-Ahead Log）** 保证原子性

#### 回滚日志模式（默认）

```
写入流程：
1. 将原始页面内容写入 .db-journal 文件（备份）
2. 修改数据库文件中的页面
3. 提交成功后删除 journal 文件

崩溃恢复：
- 如果 journal 文件存在，说明上次写入未完成
- 从 journal 恢复原始数据 → 数据库回到一致状态
```

#### WAL 模式（推荐用于嵌入式）

```
写入流程：
1. 新数据追加写入 .db-wal 文件
2. 读操作仍然读取原数据库文件（读写不冲突！）
3. 检查点（checkpoint）时将 WAL 内容合并回数据库文件

优势：
- 读写可以并发，不会互相阻塞
- 写入是顺序追加，对 Flash 更友好
```

### VDBE：SQL 的执行引擎

SQLite 并不直接"解释"SQL，而是将 SQL 编译为 **字节码**，由虚拟数据库引擎（VDBE）执行。这类似于 Java 的 JVM。

```sql
-- 这条 SQL
SELECT name FROM devices WHERE type = 'sensor';

-- 会被编译为类似这样的字节码：
-- OpenRead    0  2  0   (打开 devices 表)
-- Rewind      0  8  0   (游标移到第一行)
-- Column      0  2  1   (读取 type 列)
-- Ne          1  7  2   (如果不等于 'sensor'，跳到第7条)
-- Column      0  1  3   (读取 name 列)
-- ResultRow   3  1  0   (输出结果)
-- Next        0  2  0   (移到下一行)
-- Halt        0  0  0   (结束)
```

你可以用 `EXPLAIN` 命令查看任何 SQL 语句的字节码：
```sql
EXPLAIN SELECT name FROM devices WHERE type = 'sensor';
```

### VFS：操作系统抽象层

VFS（Virtual File System）将所有操作系统相关的操作抽象为接口：

| VFS 接口 | 功能 |
|-----------|------|
| `xOpen` | 打开文件 |
| `xRead` / `xWrite` | 读写文件 |
| `xLock` / `xUnlock` | 文件锁（实现并发控制） |
| `xSync` | 刷新到磁盘（`fsync`） |
| `xSleep` / `xCurrentTime` | 时间相关操作 |

**对嵌入式的意义**：你可以实现自定义 VFS，将 SQLite 移植到任何平台（RTOS、裸机、自定义文件系统）。例如：
- 基于 SPI Flash 的 VFS
- 基于 FreeRTOS 文件系统的 VFS
- 内存映射的 VFS（用于纯 RAM 数据库）

### 锁机制

SQLite 使用文件级别的锁来管理并发，锁的状态从轻到重依次为：

```
UNLOCKED → SHARED → RESERVED → PENDING → EXCLUSIVE
  (无锁)    (读锁)   (准备写)   (等待写)   (独占写)
```

- 多个进程可以同时持有 SHARED 锁（并发读）
- 只有一个进程能持有 EXCLUSIVE 锁（写入时独占）
- WAL 模式下，读写可以真正并发

### 内存使用

SQLite 的内存占用主要来自：

| 组件 | 默认大小 | 可配置 |
|------|----------|--------|
| 页面缓存 | ~2000 页 × 4KB ≈ 8MB | `PRAGMA cache_size` |
| 解析器栈 | ~几 KB | - |
| 排序缓冲区 | ~1MB | `PRAGMA temp_store` |
| 预编译语句 | 取决于 SQL 复杂度 | - |

在嵌入式系统中，可以通过以下方式限制内存使用：
```c
sqlite3_config(SQLITE_CONFIG_PAGECACHE, buffer, page_size, n_pages);
sqlite3_config(SQLITE_CONFIG_HEAP, heap_buf, heap_size, min_alloc);
```

## 1.7 本章小结

- 数据库是管理结构化数据的专用软件，解决了文件存储的查询、一致性、并发等问题
- 关系型数据库用"表"来组织数据，表本质上就是"带类型的结构体数组"
- SQL 是操作关系型数据库的标准语言
- SQLite 是最适合嵌入式场景的数据库

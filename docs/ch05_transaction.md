## 5.1 什么是事务？

**事务（Transaction）** 是一组作为整体执行的 SQL 操作——要么全部成功，要么全部撤销。

事务解决的不是“单条 SQL 会不会执行”，而是：

> 当多个步骤共同构成一个完整业务动作时，如何保证这几个步骤作为一个整体成功或失败。

例如，在设备数据场景里，下面这些动作都很像一个事务：

1. 新增一台设备；
2. 给设备写入初始配置；
3. 记录一条审计日志；

如果前两步成功、第三步失败，而系统又没有回滚机制，就会留下“不完整状态”的数据。事务的核心价值，就是避免这种中间状态被永久写入数据库。

### 嵌入式类比

想象你在更新 Flash 中的固件配置：

```
步骤1: 擦除旧配置区
步骤2: 写入新配置数据
步骤3: 更新校验和
```

如果步骤2执行到一半时断电了会怎样？配置数据被破坏，设备可能无法启动。

**事务就是解决这个问题的机制**——它保证这三个步骤要么全部完成，要么全部回滚到初始状态。

### 为什么“整体性”比“单条成功”更重要

很多初学者会觉得：只要每条 SQL 都执行成功，不就行了吗？

问题在于，业务正确性往往不是由某一条 SQL 单独保证的，而是由多条 SQL 的组合结果保证的。

例如：

1. 先从账户 A 扣款；
2. 再向账户 B 加款；

如果只执行了第一条就崩溃了，那么数据库里就会出现“钱被扣了，但没到账”的错误状态。事务就是为了避免这种“只做了一半”的问题。

### ACID 特性

事务具有四个特性（面试高频题）：

| 特性 | 英文 | 含义 | 嵌入式类比 |
|------|------|------|-----------|
| **原子性** | Atomicity | 事务内的操作要么全部完成，要么全部不做 | 类似 DMA 传输——传完或不传 |
| **一致性** | Consistency | 事务前后数据都处于合法状态 | CRC 校验通过 |
| **隔离性** | Isolation | 并发事务互不干扰 | 互斥锁 (mutex) |
| **持久性** | Durability | 一旦提交，数据永久保存 | 写入 Flash 后不会丢失 |

这四个特性里，对初学 SQLite 最重要的是先真正理解下面两点：

1. **原子性**：一组操作不能只做一半。
2. **持久性**：一旦提交，结果就应该被可靠保存。

而隔离性和一致性，会在你开始考虑并发访问、约束校验和崩溃恢复时越来越重要。

## 5.2 SQLite 事务语法

```sql
-- 开始事务
BEGIN TRANSACTION;

-- 执行一系列操作
INSERT INTO sensor_data (...) VALUES (...);
UPDATE devices SET ...;

-- 提交事务（使所有更改生效）
COMMIT;

-- 或者回滚事务（撤销所有更改）
ROLLBACK;
```

这三条语句可以先建立一个最基本的心智模型：

1. `BEGIN`：告诉 SQLite，“接下来多条语句要算作一个整体”。
2. `COMMIT`：确认这组操作全部生效。
3. `ROLLBACK`：放弃这组操作，撤销事务中尚未提交的更改。

### 一个最小事务流程

下面是最典型的事务写法：

```sql
BEGIN TRANSACTION;

INSERT INTO sensor_data (...) VALUES (...);
INSERT INTO sensor_data (...) VALUES (...);
UPDATE devices SET ...;

COMMIT;
```

如果中间发现任何一步失败，或者业务检查不通过，就应该执行：

```sql
ROLLBACK;
```

而不是继续带着错误状态往下走。

### `BEGIN TRANSACTION` 的直观含义

对 SQLite 来说，事务开始后，后续的修改不会被立即作为一个个独立最终结果写入，而是先被放进同一组事务上下文中。直到 `COMMIT`，SQLite 才会把这一组修改正式提交。

因此可以把事务理解成：

> 先把一批修改临时打包，确认没问题后再一次性生效。

### 隐式事务

> **重要**：如果你不显式使用 `BEGIN/COMMIT`，SQLite 会为每条 SQL 语句自动创建一个事务。这意味着每条 INSERT 都会触发一次磁盘同步——这在批量插入时**非常慢**！

```
// 不使用事务：1000 条 INSERT = 1000 次磁盘同步 ≈ 很慢
// 使用事务：  1000 条 INSERT = 1 次磁盘同步 ≈ 很快
```

### 为什么隐式事务会慢

如果你不写 `BEGIN/COMMIT`，SQLite 会默认把每一条 `INSERT`、`UPDATE`、`DELETE` 都当成一个独立事务。

这意味着下面这段逻辑：

1. 插入 1 条记录；
2. 提交；
3. 再插入 1 条记录；
4. 再提交；
5. 重复 5000 次；

会触发大量重复的事务提交和磁盘同步开销。

而如果包在一个显式事务里：

1. 先 `BEGIN`；
2. 连续插入 5000 条；
3. 最后只 `COMMIT` 一次；

那么大量固定开销就被摊薄了，所以性能通常会显著提升。

这就是为什么数据库开发里有一句非常实用的原则：

> 批量写入时，几乎总是要显式使用事务。

### 事务不只是为了正确性，也是为了性能

很多人第一次接触事务时，只把它看成“失败时回滚”的安全机制。实际上，在 SQLite 这类嵌入式数据库里，事务还有一个非常现实的价值：

> 它也是最重要的批量写入性能优化手段之一。

因此，事务同时解决两类问题：

1. 业务正确性问题；
2. 批量写入性能问题。

### SQLite 中几种常见的事务开始方式

本章示例使用的是：

```sql
BEGIN TRANSACTION;
```

但 SQLite 还支持一些更细化的写法，例如：

1. `BEGIN DEFERRED`：默认模式，真正需要写时才申请写锁。
2. `BEGIN IMMEDIATE`：一开始就尝试获得写事务所需的保留锁。
3. `BEGIN EXCLUSIVE`：更强的独占语义。

对入门阶段来说，先掌握 `BEGIN TRANSACTION` 已经足够。后面遇到多连接竞争写锁的问题时，再去区分这些模式会更合适。

## 5.3 SQLite 的锁机制

SQLite 使用文件级锁来控制并发访问：

```
锁状态升级过程：

  UNLOCKED  →  SHARED  →  RESERVED  →  PENDING  →  EXCLUSIVE
  (无锁)       (读锁)     (预写锁)     (等待锁)     (写锁)
                 │
                 └── 多个连接可以同时持有 SHARED 锁（允许并发读）
                       但同一时刻只能有一个 EXCLUSIVE 锁（互斥写）
```

| 锁类型 | 允许并发读 | 允许并发写 |
|--------|-----------|-----------|
| SHARED | ✅ 是 | ❌ 否 |
| EXCLUSIVE | ❌ 否 | ❌ 否 |

> **嵌入式工程师注意**：SQLite 的并发模型类似于读写锁（`pthread_rwlock`）——多个线程可以同时读，但写操作需要独占访问。

### 为什么 SQLite 的并发和服务端数据库不一样

像 MySQL、PostgreSQL 这类服务端数据库有独立数据库进程和更复杂的锁管理机制，而 SQLite 本质上是一个直接操作数据库文件的嵌入式库。

这意味着：

1. 数据库就是一个普通文件；
2. 多个连接的协调，要靠文件锁和日志机制实现；
3. 它的设计目标更偏向轻量、可靠、易嵌入，而不是极端高并发写入。

所以 SQLite 的经典并发特征是：

> 读并发友好，写并发受限，同一时刻只有一个写者。

### 如何理解锁状态升级

图里的状态可以先按“是否准备写入”来理解，而不必一开始死记全部细节：

1. `SHARED`：表示当前连接正在读，允许其他连接也读。
2. `RESERVED`：表示某个连接已经声明“我之后要写”。
3. `EXCLUSIVE`：表示真正进入独占写阶段，其他连接不能再读写这个数据库文件。

从工程直觉上看，这很像：

1. 大家都能看共享数据；
2. 某个任务先举手预约写入；
3. 真正动手改的时候，必须独占现场。

### 事务和锁的关系

一旦事务里包含写操作，SQLite 就需要考虑写锁问题。

也就是说：

1. 事务定义“哪些语句属于一个整体”；
2. 锁机制定义“这个整体执行时，如何和其他连接协调访问”。

因此，事务和并发控制虽然是两个概念，但在实际运行中是紧密耦合的。

### 为什么会出现“数据库忙”

当一个连接已经持有写相关锁，而另一个连接又想开始写，或者读写冲突无法立即协调时，就可能出现 `database is locked` 或 `busy` 类错误。

这类问题的根源通常不是 SQL 写错了，而是：

1. 同时有多个连接竞争写入；
2. 某个事务持锁时间太长；
3. 日志模式和并发模式不适合当前负载。

这也是为什么 WAL 模式会在很多场景下明显改善体验。

## 5.4 WAL 模式

SQLite 默认使用 **Rollback Journal** 模式，每次写操作都会阻塞所有读操作。

**WAL（Write-Ahead Logging）** 模式改善了这个问题：

```
Rollback Journal 模式：            WAL 模式：
  写操作 → 阻塞所有读操作           写操作 → 不阻塞读操作
  读操作 → 阻塞写操作               读操作 → 不阻塞写操作
                                    (读和写可以并发！)
```

启用 WAL 模式：

```sql
PRAGMA journal_mode = WAL;
```

WAL 模式的优缺点：

| 优点 | 缺点 |
|------|------|
| 读写可以并发 | 多了 `-wal` 和 `-shm` 文件 |
| 写入性能更好 | 不支持网络文件系统（NFS） |
| 崩溃恢复更快 | 需要共享内存支持 |

### 为什么 WAL 更适合现代应用场景

默认的 Rollback Journal 模式更容易从“回滚旧版本”的角度理解，而 WAL 则是“先把新内容写到预写日志里”。

对使用者来说，最重要的感知差异不是内部格式，而是并发行为：

1. 在默认模式下，写操作和读操作更容易互相阻塞；
2. 在 WAL 模式下，读者通常可以继续读旧快照，而写者把新变更追加到 WAL 文件中。

这就使得“读写并发”变得更现实。

### `PRAGMA journal_mode = WAL` 会发生什么

示例代码里做了两次查询：

1. 先查当前 `journal_mode`；
2. 再执行 `PRAGMA journal_mode = WAL;`；

这是一个很好的教学点，因为它说明 `PRAGMA` 不只是“设置开关”，也能直接返回设置结果。

因此：

```sql
PRAGMA journal_mode = WAL;
```

不仅是在发出切换请求，也是在让 SQLite 告诉你“实际切换后的模式是什么”。

### 为什么会多出 `-wal` 和 `-shm` 文件

启用 WAL 后，SQLite 通常会在原数据库文件旁边生成：

1. `xxx.db-wal`
2. `xxx.db-shm`

可以先用直观方式理解：

1. `-wal` 文件保存预写日志内容；
2. `-shm` 文件用于共享内存协调信息。

这也是为什么示例程序在结束时会顺手删除这两个文件。

### WAL 不是“永远更快”，但通常更实用

对入门教学来说，可以先记住：WAL 在很多读多写少或读写并发的应用里表现很好。但这并不意味着它在所有场景下都绝对优于默认模式。

真正该掌握的是：

1. 它改变了并发行为；
2. 它常常改善读写互斥问题；
3. 它在嵌入式本地存储场景中很常见；
4. 但仍然要根据部署环境选择。

## 5.5 SAVEPOINT 与部分回滚

除了“整个事务提交”或“整个事务回滚”之外，SQLite 还支持更细粒度的控制，这就是 `SAVEPOINT`。

它适合下面这种需求：

1. 一个大事务已经开始；
2. 中途某一小段操作可能失败；
3. 希望撤销这一小段，但保留事务前面已经确认没问题的部分。

### 基本语法

```sql
SAVEPOINT sp1;

-- 一些可能失败的操作
INSERT INTO ...;
UPDATE ...;

ROLLBACK TO sp1;
RELEASE sp1;
```

### `SAVEPOINT`、`ROLLBACK TO`、`RELEASE` 各自做什么

可以把它们理解成事务内部的小书签：

1. `SAVEPOINT sp1`：在当前事务中做一个标记点。
2. `ROLLBACK TO sp1`：撤销从这个标记点之后发生的修改，但事务本身还继续存在。
3. `RELEASE sp1`：确认不再需要这个保存点。

这里最容易混淆的是：

> `ROLLBACK` 是回滚整个事务，`ROLLBACK TO savepoint` 是只回滚到某个中间点。

### 为什么 SAVEPOINT 很实用

对于复杂业务流程来说，很多时候并不是“整个事务都错了”，而是“事务中的某个局部步骤出了问题”。

例如：

1. 前半部分数据已经校验通过；
2. 某个候选写入值被发现异常；
3. 你只想撤销异常部分，再换一组数据继续；

这正是 `SAVEPOINT` 的典型应用场景。

### 本章示例里的 SAVEPOINT 在演示什么

示例代码中：

1. 先插入第 1 条正常数据；
2. 建立保存点 `sp1`；
3. 再插入一条“异常数据”；
4. 发现异常后执行 `ROLLBACK TO sp1`；
5. 然后改插一条正常数据；
6. 最后 `COMMIT` 整个事务。

这个过程非常适合帮助读者建立一个重要直觉：

> 事务不是只有“全有”或“全无”两种粗粒度控制，`SAVEPOINT` 可以在事务内部提供更精细的回退能力。

## 5.6 示例代码讲解

cd build && ./ch05_transaction

### 代码结构总览

这个示例程序主要分成四段：

1. 先准备一张 `sensor_data` 表；
2. 对比“无事务批量插入”和“有事务批量插入”的性能；
3. 演示 `ROLLBACK` 和 `SAVEPOINT`；
4. 查看并切换 `journal_mode`，再观察 WAL 下的写入表现。

### `count_rows()` 这个辅助函数在做什么

```cpp
static int count_rows(sqlite3 *db, const char *table)
```

这个函数的作用很简单：动态拼出：

```sql
SELECT COUNT(*) FROM 表名;
```

然后通过 `sqlite3_prepare_v2()`、`sqlite3_step()`、`sqlite3_column_int()` 读取结果。

教学上它很有价值，因为它把“执行一条返回单个数值的查询”这个基本模式写得非常清楚：

1. `prepare`
2. `step`
3. `column`
4. `finalize`

### 1. 性能对比：为什么同样是 5000 条插入，时间会差很多

示例程序先做“无事务插入 5000 条”，再清空表，然后再做“有事务插入 5000 条”。

两段代码的循环体几乎一样，唯一核心差别就是第二段外面多了：

```cpp
BEGIN TRANSACTION;
...
COMMIT;
```

这是一种非常好的实验设计，因为它让你能把性能差异主要归因到“是否使用显式事务”，而不是其他变量。

这里的结论通常会非常明显：

1. 无事务时，每条插入都像一次独立提交；
2. 有事务时，5000 条插入被打包成一次提交；
3. 因此耗时差距往往非常大。

### 2. `ROLLBACK` 演示为什么能看到“事务内已插入 2 条”

示例里有一段很容易让初学者疑惑：

1. 开启事务；
2. 插入 2 条记录；
3. 在 `COMMIT` 前查询记录数；
4. 显示已经有 2 条；
5. 然后 `ROLLBACK`；
6. 再查又变成 0 条。

这说明：

> 事务中的修改，在当前事务上下文里是可见的，但在未提交前仍然可以整体撤销。

这也是事务非常关键的概念之一：未提交不等于完全不存在，而是“仍处于可撤销状态”。

### 3. SAVEPOINT 演示的是“局部回滚，不是整事务作废”

示例里通过 `SAVEPOINT sp1`、`ROLLBACK TO sp1`、`RELEASE sp1` 展示了事务内部的阶段性控制。

它最值得学习的不是语法本身，而是处理思路：

1. 先保留已经确认无误的写入；
2. 对可疑步骤单独设保存点；
3. 出现异常时只撤销后半段；
4. 修正后继续向前推进；
5. 最终再统一提交。

这是很符合真实业务逻辑的工程写法。

### 4. `PRAGMA journal_mode` 的读取和设置方式

示例程序先执行：

```cpp
sqlite3_prepare_v2(db, "PRAGMA journal_mode;", -1, &stmt, nullptr);
```

再执行：

```cpp
sqlite3_prepare_v2(db, "PRAGMA journal_mode = WAL;", -1, &stmt, nullptr);
```

两次都通过 `sqlite3_step()` + `sqlite3_column_text()` 读取返回值。这再次说明一个很重要的实践点：

> 很多 `PRAGMA` 语句本身就会返回结果，因此它们在 C API 层面更像查询，而不是单纯的设置命令。

### 5. 这个示例为什么特别适合初学者

因为它不是只给出语法，而是把事务最关键的三个学习目标都做成了可观察现象：

1. **性能差异**：无事务和有事务的时间对比；
2. **正确性保障**：`ROLLBACK` 后数据被撤销；
3. **更细粒度控制**：`SAVEPOINT` 允许部分回滚；

再加上 `WAL` 模式切换，这一章已经把“事务”和“并发控制”的基础核心完整串起来了。

## 5.7 本章小结

- **事务** 保证一组操作的原子性——要么全部成功，要么全部回滚
- **批量操作务必使用事务**——性能差距可达 100 倍以上
- SQLite 使用文件级锁，同一时刻只能有一个写者
- **WAL 模式** 允许读写并发，推荐在嵌入式场景中使用
- `SAVEPOINT` 提供事务内的部分回滚能力

### 把本章浓缩成一套心智模型

如果要把第五章浓缩成几句话，可以记成：

1. 事务负责把多条 SQL 变成一个不可分割的整体。
2. `COMMIT` 让这组修改永久生效，`ROLLBACK` 撤销整个事务。
3. `SAVEPOINT` 让你在事务内部做阶段性回退。
4. 锁机制决定多个连接同时访问时，谁能读、谁能写。
5. `WAL` 改善了读写并发，是 SQLite 很重要的运行模式。

### 从本章进入下一章前，你应该已经掌握什么

如果这一章内容已经掌握，你应该能够：

1. 理解为什么批量写入必须优先考虑显式事务。
2. 能看懂 `BEGIN / COMMIT / ROLLBACK / SAVEPOINT / RELEASE` 的基本流程。
3. 明白 SQLite 的并发特点是“多读单写”。
4. 理解 WAL 模式为什么会改变读写阻塞关系。
5. 能把事务同时看成“正确性工具”和“性能优化工具”。

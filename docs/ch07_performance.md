# 第七章：性能优化与最佳实践

### 本章会学到什么

学完这一章后，你应该能理解下面这些问题：

1. 为什么 SQLite 的最大性能瓶颈通常不是 SQL 解析，而是磁盘同步和 I/O。
2. 为什么“事务 + 预编译语句复用”通常是最重要的两项优化。
3. 索引为什么既能显著提速，也可能拖慢写入。

5. `VACUUM`、`ANALYZE`、`integrity_check` 分别适合什么时候做。
6. 怎样根据嵌入式设备的存储、内存和可靠性约束来调整 SQLite 配置。

## 7.1 SQLite 性能优化核心原则

对于嵌入式系统，性能优化通常聚焦于两个方面：**减少磁盘 I/O** 和 **减少 CPU 计算**。

```
性能瓶颈排名：

  磁盘同步 (fsync)  >>>>  磁盘读写  >>  CPU 计算  >  内存分配
  (最慢，差距巨大)        (较慢)        (较快)       (最快)
```

这张图要表达的核心不是“CPU 不重要”，而是：

> 在 SQLite 这类本地嵌入式数据库里，真正容易把程序拖慢的，往往不是算术计算，而是磁盘相关操作。

### 为什么磁盘同步特别慢

当数据库执行事务提交时，通常需要把关键数据真正落盘。这个过程比纯内存计算慢得多，因为它涉及：

1. 内核缓存刷新；
2. 文件系统同步；
3. 存储介质实际写入；
4. 某些情况下的日志文件更新。

所以在 SQLite 优化里，一个非常重要的原则是：

> 尽量减少“必须立即持久化”的次数。

这也是为什么显式事务能带来巨大性能提升。

### 优化时先抓大头，不要先抠细节

SQLite 性能优化最容易走偏的一点是：一开始就试图优化微小的 C++ 代码细节，而忽略真正大的成本来源。

通常更正确的顺序是：

1. 先减少事务提交次数；
2. 再避免重复编译 SQL；
3. 再用索引优化查询路径；
4. 然后再看 `PRAGMA` 调优；
5. 最后才考虑更细枝末节的优化。

这也是本章的整体组织顺序。

## 7.2 关键优化手段

### 1. 使用事务包裹批量操作

这是**最重要的优化**，可以提升 10-100 倍性能（第五章已详细介绍）。

它之所以重要，是因为：

1. 不使用显式事务时，每条写入都可能变成独立提交；
2. 每次提交都可能触发昂贵的同步开销；
3. 批量数据如果被拆成成千上万次小提交，就会非常慢。

而用事务后：

1. 多条写入先在一个事务里累积；
2. 最后统一 `COMMIT`；
3. 大量固定开销只付一次。

因此，对批量写入场景来说，事务通常是“第一优先级优化项”。

### 2. 预编译语句复用

```cpp
// ❌ 每次都编译 SQL（慢）
for (int i = 0; i < 1000; i++) {
    sqlite3_exec(db, "INSERT ...", ...);  // 每次都编译+执行
}

// ✅ 编译一次，执行多次（快）
sqlite3_prepare_v2(db, "INSERT ... VALUES (?, ?)", ...);
for (int i = 0; i < 1000; i++) {
    sqlite3_bind_*(...);
    sqlite3_step(stmt);
    sqlite3_reset(stmt);  // 重置后复用
}
sqlite3_finalize(stmt);
```

这项优化的本质是：

1. SQL 文本解析和编译也是有成本的；
2. 如果同一条 SQL 要执行成千上万次，没有必要每次都重新编译；
3. 应该先 `prepare` 一次，再不断 `bind + step + reset` 复用。

这尤其适合：

1. 批量插入；
2. 批量更新；
3. 循环查询；
4. 周期性采样写库。

因此，性能优化里一个非常实用的口诀是：

> 相同 SQL 模板重复执行时，优先复用 `sqlite3_stmt`。

### 3. 合理使用索引

- 对 `WHERE`、`JOIN`、`ORDER BY` 中频繁出现的列创建索引
- 避免过多索引（每个索引都会降低写入速度）

索引的核心价值是减少查询时扫描的数据量。但它不是白来的，因为每次插入、更新、删除都要同步维护索引结构。

所以索引的正确思路不是“能建就建”，而是：

1. 先找出最常用、最慢的查询；
2. 看它们主要依赖哪些筛选列、关联列、排序列；
3. 再给这些真正高价值的列建索引。

### 4. PRAGMA 调优

```sql
-- 设置缓存大小（页面数，默认 -2000 即约 2MB）
PRAGMA cache_size = -8000;  -- 约 8MB 缓存

-- 同步模式（影响数据安全性 vs 性能）
PRAGMA synchronous = NORMAL;  -- 性能与安全的平衡
-- FULL: 最安全但最慢
-- NORMAL: 推荐，极小概率丢失最近一次事务
-- OFF: 最快但断电可能损坏数据库

-- 临时存储位置
PRAGMA temp_store = MEMORY;  -- 临时表和索引放在内存中

-- 内存映射 I/O
PRAGMA mmap_size = 268435456;  -- 256MB 内存映射
```

`PRAGMA` 调优的本质，是在不同设备和业务目标下，重新平衡：

1. 安全性；
2. 写入速度；
3. 读取速度；
4. 内存占用；
5. 临时文件开销。

下面这些项最值得优先理解。

#### `journal_mode`

示例代码里使用了：

```sql
PRAGMA journal_mode = WAL;
```

它的主要意义是改善读写并发，并常常带来更好的实际写入体验。对很多本地数据库应用来说，WAL 是非常常见的推荐设置。

#### `synchronous`

这是 SQLite 性能调优中非常关键的开关之一。

可以粗略理解为：

1. `FULL`：最谨慎，最安全，但最慢；
2. `NORMAL`：通常是工程上很好的折中；
3. `OFF`：追求极致速度，但断电或崩溃时风险很高。

因此，大多数嵌入式业务代码不会轻易把它调到 `OFF`，而更常见的是在 `FULL` 和 `NORMAL` 之间权衡。

#### `cache_size`

它决定 SQLite 允许自己保留多少页面缓存。缓存足够大时：

1. 可减少反复读盘；
2. 有利于热点数据访问；
3. 但也会占用更多 RAM。

所以它和设备内存预算直接相关。

#### `temp_store`

某些排序、临时索引、中间结果会用到临时存储。设置成 `MEMORY` 可以减少临时文件 I/O，但会多占一点内存。

这对内存相对充足的设备通常是有利的。

#### `mmap_size`

内存映射 I/O 可以在某些场景下降低访问开销，但它并不是所有项目都必须开启的第一优先级优化。它更像是在完成事务、索引、缓存等基础优化后，再考虑的高级调优项。

### 5. 数据库维护

```sql
-- 回收已删除数据的空间
VACUUM;

-- 分析表统计信息（帮助查询优化器选择最佳执行计划）
ANALYZE;

-- 完整性检查
PRAGMA integrity_check;
```

性能优化不仅是“执行时怎么更快”，还包括“数据库长期运行后怎么保持健康”。

#### `VACUUM`

当大量数据被删除后，数据库文件不一定会立刻变小，因为空闲页往往只是留在数据库内部等待复用。`VACUUM` 会重建数据库文件，从而回收空间并整理布局。

它适合：

1. 删除了大量历史数据之后；
2. 数据库文件明显膨胀时；
3. 做阶段性维护时。

#### `ANALYZE`

`ANALYZE` 会更新统计信息，帮助查询优化器更准确地判断该走哪个索引、用什么执行计划。

因此它更像是“让数据库更懂自己的数据分布”。

#### `integrity_check`

这个不是性能优化命令，而是健康检查命令。但在维护场景里，它很重要，因为优化不能以牺牲数据库完整性为代价。

## 7.3 嵌入式场景的特殊考量

| 场景 | 建议 |
|------|------|
| Flash 存储（SD卡、eMMC） | 使用 WAL 模式减少写放大 |
| 内存受限 | 减小 `cache_size`，使用 `temp_store = FILE` |
| 频繁写入 | 合并写操作到事务中，使用 `synchronous = NORMAL` |
| 数据量大 | 创建适当索引，定期 VACUUM |
| 需要高可靠性 | 保持 `synchronous = FULL`，定期备份 |

这一节最重要的是建立一个观念：

> 性能优化不是只追求“更快”，而是在特定硬件和业务约束下做取舍。

### Flash 存储设备为什么要特别注意写放大

在 SD 卡、eMMC、Flash 芯片等介质上，写入不仅慢，还可能影响寿命。频繁的小写入、频繁同步和频繁碎片化更新，都会增加实际写放大。

因此嵌入式场景特别重视：

1. 批量事务；
2. 减少不必要索引；
3. 更合适的日志模式；
4. 更稳妥的同步等级选择。

### 内存受限设备不要盲目照搬桌面配置

在桌面和服务器上，给 SQLite 多分配几 MB 缓存可能完全不痛不痒；但在 MCU、边缘网关、轻量 Linux 板卡上，这可能就非常敏感。

所以：

1. `cache_size` 不宜盲目调大；
2. `temp_store = MEMORY` 也不是永远正确；
3. 应该根据设备 RAM 实际预算来调。

### 高可靠性设备和高吞吐设备的优化方向不同

如果你的目标是“绝不轻易丢最近一次事务”，那么就应更偏向安全配置；如果目标是“高频采样快速落盘”，那么可以适度向性能倾斜。

这意味着优化方案不能脱离业务目标孤立讨论。

## 7.4 示例代码讲解

完整示例：[examples/ch07_performance.cpp](../examples/ch07_performance.cpp)

运行方式：

```bash
cd build && ./ch07_performance
```

### 代码结构总览

这个示例程序一共做了 7 件事：

1. 应用 `PRAGMA` 优化设置并打印当前配置；
2. 用事务 + 预编译语句批量插入 50000 条数据；
3. 对比无索引和有索引时的查询耗时；
4. 查看 `EXPLAIN QUERY PLAN` 输出；
5. 删除部分数据并演示 `VACUUM`；
6. 执行完整性检查；
7. 执行 `ANALYZE` 更新统计信息。

这使它成为一份很实用的“性能优化实验台”示例。

### 1. PRAGMA 设置为什么放在最前面

示例一开始就设置：

1. `journal_mode = WAL`
2. `synchronous = NORMAL`
3. `cache_size = -8000`
4. `temp_store = MEMORY`

这是因为后续插入、查询、维护操作都会受到这些参数影响。如果先跑测试再改配置，就很难解释结果到底受哪些因素影响。

因此这种写法在教学上很合理：

> 先明确运行环境，再测性能。

### 2. 批量插入示例同时演示了两类关键优化

这段代码最值得注意的，不只是“插了 50000 条”，而是它把两项最核心优化叠加在了一起：

1. 使用事务：`BEGIN TRANSACTION` 到 `COMMIT`
2. 复用预编译语句：`prepare` 一次，循环里反复 `bind + step + reset`

这意味着示例不是在展示“某一个孤立技巧”，而是在展示一套现实中非常常见的高性能写入模式。

### 3. 无索引 vs 有索引查询为什么要重复 100 次

示例没有只跑一次查询，而是把同一类查询重复执行 100 次。这是个很好的实验设计，因为：

1. 单次查询时间可能太短，难以比较；
2. 重复多次后，差异更容易稳定地体现出来；
3. 更接近真实系统中“同类查询反复发生”的情况。

### 4. `EXPLAIN QUERY PLAN` 是把“快”变成“可解释”

仅仅看到“有索引更快”还不够，示例还进一步打印了执行计划：

```sql
EXPLAIN QUERY PLAN SELECT * FROM sensor_data WHERE device_id = 1 AND temperature > 25;
```

这一步很重要，因为它把“速度结果”变成了“执行路径证据”。

换句话说：

1. 计时告诉你有没有变快；
2. 执行计划告诉你为什么变快。

### 5. VACUUM 演示最容易帮助初学者建立正确直觉

这段示例先查看数据库大小，再删除一半数据，再查看一次大小，然后执行 `VACUUM` 再看大小。

它展示了一个非常关键的事实：

> 删除记录并不等于数据库文件立刻缩小。

这能帮助读者理解为什么生产环境里“表里数据少了，但数据库文件还是很大”并不奇怪。

### 6. `integrity_check` 和 `ANALYZE` 为什么放在最后

因为这两项更像维护动作，而不是直接的业务读写动作。

1. `integrity_check` 确认数据库状态健康；
2. `ANALYZE` 更新统计信息，让优化器更了解当前数据分布。

把它们放在最后，符合“先完成主要操作，再做维护和验证”的节奏。

## 7.5 本章小结

性能优化优先级（从高到低）：

1. **使用事务** —— 最大的性能提升
2. **预编译语句复用** —— 避免重复编译 SQL
3. **创建索引** —— 加速查询
4. **PRAGMA 调优** —— `synchronous`、`cache_size`、`WAL`
5. **定期维护** —— `VACUUM`、`ANALYZE`

### 把本章浓缩成一套心智模型

如果要把第七章压缩成最核心的几句话，可以记成：

1. SQLite 的大头成本通常在磁盘同步和 I/O，不在 CPU 算术。
2. 批量写入时，事务和语句复用往往是最先该做、收益最大的优化。
3. 索引优化的是查询路径，但会增加写入维护成本。
4. `PRAGMA` 调优本质是在安全性、内存和速度之间做取舍。
5. 性能优化不是一次性动作，`VACUUM`、`ANALYZE` 和健康检查也是长期维护的一部分。

### 从本章进入下一章前，你应该已经掌握什么

如果这一章已经掌握，你应该能够：

1. 识别 SQLite 性能瓶颈通常更接近 I/O 而不是纯计算。
2. 用事务和预编译语句写出高效的批量插入代码。
3. 理解索引何时值得建立、何时会拖慢写入。
4. 根据设备特性调整 `WAL`、`synchronous`、`cache_size`、`temp_store` 等配置。
5. 知道在数据库长期运行后如何用 `VACUUM`、`ANALYZE` 和 `integrity_check` 做维护。

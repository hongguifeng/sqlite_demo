### 本章会学到什么

学完这一章后，你应该能理解下面这些问题：

1. 为什么嵌入式项目里更适合把 SQLite 封装成模块化类接口，而不是到处散写 SQL。
2. 一个数据采集系统为什么至少要同时管理设备表、数据表、告警规则表和告警事件表。

## 8.1 场景描述

假设你正在开发一个 IoT 网关设备，需要：

1. 管理多个传感器设备的注册信息。
2. 采集并存储传感器数据（温度、湿度）。
3. 设置告警规则并记录告警事件。
4. 定期清理过期数据。
5. 支持数据查询和统计。

这其实已经非常接近真实嵌入式系统的基本需求了。因为在很多边缘设备、工业采集终端、环境监测网关里，数据库并不是“附属功能”，而是系统稳定运行的一部分基础设施。

### 为什么这个案例很典型

这个案例之所以适合当实战章节，是因为它把前面学过的知识都自然串起来了：

1. 设备注册需要基本 CRUD。
2. 采样写入需要高频插入和批量事务。
3. 告警规则需要条件判断和事件记录。
4. 数据概览需要聚合查询和多表关联。
5. 长期运行需要清理、检查和调优。

因此，本章的重点不只是“把代码跑起来”，而是：

> 理解一个嵌入式数据库系统为什么要这么设计。

## 8.2 数据库设计

```
┌──────────────┐       ┌──────────────────┐
│   devices    │       │   sensor_data     │
│──────────────│       │──────────────────│
│ device_id PK │──┐    │ id PK            │
│ name         │  │    │ device_id FK ─────┤
│ type         │  └───→│ temperature      │
│ location     │       │ humidity          │
│ status       │       │ timestamp        │
│ created_at   │       └──────────────────┘
└──────────────┘
        │              ┌──────────────────┐
        │              │   alert_rules     │
        └─────────────→│ id PK            │
                       │ device_id FK     │
                       │ metric           │
                       │ threshold        │
                       │ condition        │
                       └──────────────────┘
                               │
                       ┌───────┴──────────┐
                       │   alert_events    │
                       │ id PK            │
                       │ rule_id FK       │
                       │ device_id FK     │
                       │ value            │
                       │ timestamp        │
                       └──────────────────┘
```

### 4 张表分别在解决什么问题

这套设计不是为了“表越多越专业”，而是因为每张表承担的职责不同。

#### 1. `devices`

这张表是设备主表，用来记录：

1. 设备是谁；
2. 设备类型是什么；
3. 安装位置在哪里；
4. 当前状态如何；
5. 什么时候注册进系统。

你可以把它理解成“设备资产台账”。

#### 2. `sensor_data`

这张表是采样明细表，用来保存每一次采样结果。它和 `devices` 是典型的一对多关系：

1. 一台设备会对应很多条采样记录；
2. 每条采样记录只属于一台设备。

因此它更像“时序数据明细表”。

#### 3. `alert_rules`

这张表保存的是规则定义，而不是实际告警本身。

例如：

1. 温度 `>` 30.0 就报警；
2. 湿度 `>` 80.0 就报警；
3. 室外温度 `<` -10.0 就报警；

这类“阈值条件”适合存成规则表，因为它可能随配置变化，而不应写死在代码里。

#### 4. `alert_events`

这张表保存的是“规则被触发的历史记录”。

它和 `alert_rules` 的区别非常重要：

1. `alert_rules` 记录“应该如何判断”；
2. `alert_events` 记录“什么时候真的触发了”。

只有把规则定义和告警事件分开，系统才能同时支持“改规则”和“查历史”。

### 为什么外键关系很重要

示例代码里给这些表都建立了明确的外键关系，这意味着：

1. `sensor_data.device_id` 必须对应 `devices.device_id`；
2. `alert_rules.device_id` 必须对应已有设备；
3. `alert_events.rule_id` 和 `alert_events.device_id` 也必须对应已有记录。

在嵌入式系统里，外键的意义不仅是“数据库更规范”，更重要的是：

> 它可以避免长期运行后出现越来越多的脏数据和孤儿记录。

### 为什么示例里要给 `sensor_data` 建索引

示例代码中创建了：

1. `idx_sensor_device`：按设备查询采样数据更快；
2. `idx_sensor_time`：按时间范围清理和查询更快；

这两类索引非常符合实际场景，因为嵌入式采样系统最常见的两个过滤条件就是：

1. 看某台设备的数据；
2. 清理某个时间之前的数据。

## 8.3 实现要点

### 数据库初始化封装

在嵌入式项目中，建议将数据库操作封装为模块化的函数或类：

```cpp
class SensorDatabase {
public:
    bool open(const char *path);
    void close();

    // 设备管理
    int addDevice(const char *name, const char *type, const char *location);
    bool removeDevice(int device_id);

    // 数据采集
    bool insertReading(int device_id, double temp, double humidity);

    // 告警
    bool checkAlerts(int device_id, double temp, double humidity);

    // 维护
    int cleanOldData(int days);
};
```

### 为什么嵌入式项目更需要封装数据库类

在桌面小工具里，到处写几条 SQL 也许还能接受；但在长期运行的嵌入式系统中，这种做法会很快失控。

把 SQLite 封装成类的好处主要有四点：

1. 连接生命周期更清楚：谁打开、谁关闭一目了然。
2. 初始化配置集中处理：`WAL`、`busy_timeout`、外键、缓存等都能在 `open()` 中统一设置。
3. 业务接口更稳定：上层逻辑调用的是 `addDevice()`、`insertBatch()`、`checkAndRecordAlerts()`，而不是直接拼 SQL。
4. 后续重构更容易：如果未来要补日志、补错误码、补重试、补统计，不需要到处改散落代码。

### 示例里的 `open()` 为什么做了那么多事

示例代码中的 `open()` 不只是打开数据库，它还顺手完成了：

1. `journal_mode = WAL`
2. `synchronous = NORMAL`
3. `cache_size = -2000`
4. `foreign_keys = ON`
5. `busy_timeout = 5000`
6. 表结构初始化 `initTables()`

这其实就是一个典型的“连接初始化阶段”。对嵌入式工程来说，这样做比让调用者自己记得一条条设置更安全。

### 数据采集为什么要区分单条写入和批量写入

示例同时提供了：

1. `insertReading()`：适合单条写入。
2. `insertBatch()`：适合批量采样写入。

这非常符合真实场景，因为设备有时是“来一条写一条”，有时则是“缓存一批再统一刷盘”。

而从性能上看，批量写入通常更值得优先设计，因为它可以：

1. 用事务包住整批数据；
2. 复用同一个预编译语句；
3. 大幅减少提交和编译开销。

### 告警为什么在应用层判断，而不是用数据库触发器

本章示例选择在应用层实现 `checkAndRecordAlerts()`，而不是用 SQLite 触发器。这样做的好处是：

1. 逻辑更直观，适合教学；
2. 条件判断更容易扩展；
3. 便于和设备业务状态、外部通知等逻辑集成；
4. 更方便调试和打印过程。

数据库触发器当然也能做告警，但在嵌入式项目里，很多团队仍然更愿意把复杂业务规则留在应用层，以保持控制感和可读性。

### 自动清理策略

嵌入式设备存储有限，需要定期清理旧数据：

```sql
-- 删除 30 天前的数据
DELETE FROM sensor_data
WHERE timestamp < datetime('now', '-30 days');

-- 限制总记录数（保留最新的 N 条）
DELETE FROM sensor_data
WHERE id NOT IN (
    SELECT id FROM sensor_data
    ORDER BY timestamp DESC
    LIMIT 100000
);
```

### 为什么清理策略是长期运行设备的刚需

很多初学者会把清理旧数据看成“锦上添花”的维护功能，但对嵌入式设备来说，它通常是必需项。

因为采样型系统有一个天然特点：

1. 数据持续增加；
2. 设备存储空间有限；
3. 如果没有清理策略，数据库文件只会越来越大。

因此，长期运行能力本质上依赖于：

> 你有没有设计数据生命周期策略。

### 两种清理思路分别适合什么场景

#### 1. 按时间清理

例如删除 30 天以前的数据。

适合：

1. 系统有明确保留期限；
2. 历史数据按天、按周自然过期；
3. 日志型和采样型设备场景。

#### 2. 按总量清理

例如只保留最近的 100000 条记录。

适合：

1. 存储预算是固定的；
2. 业务上更关心“最近一段数据”而不是“最近多少天”；
3. 希望对数据库体积做更强的上限控制。

这两种策略在真实系统里甚至可以同时使用。

## 8.4 示例代码讲解

完整示例：[examples/ch08_embedded.cpp](../examples/ch08_embedded.cpp)（约 400 行，包含完整的 `SensorDatabase` 类实现）

运行方式：

```bash
cd build && ./ch08_embedded
```

### 代码结构总览

这个示例可以分成两大块：

1. `SensorDatabase` 类：负责数据库连接、建表、写入、查询、维护。
2. `main()`：模拟一个嵌入式采集系统从启动到运行再到维护的完整流程。

### `SensorDatabase` 类最值得学习的地方

#### 1. `open()`：统一完成数据库初始化

它展示了一个非常重要的工程习惯：数据库连接一旦建立，就立即完成运行参数配置和表结构初始化。

这样做的好处是：

1. 每次启动环境一致；
2. 调用者不需要记住一堆初始化细节；
3. 更适合嵌入式固件里“系统启动即初始化数据库”的模式。

#### 2. `exec()`：封装简单 SQL 执行

私有函数 `exec()` 用 `sqlite3_exec()` 统一处理不需要结果集的 SQL，例如：

1. 建表；
2. 建索引；
3. `PRAGMA` 设置；
4. 简单删除；
5. 事务控制语句。

这说明一个很实用的封装原则：

> 对“无结果集”的 SQL，可以统一走一个简单执行入口。

#### 3. `initTables()`：把数据库结构当成系统的一部分

这个函数不是附属工具，而是整个系统启动过程的一部分。它把：

1. 表结构；
2. 约束；
3. 索引；

都固定在程序里，让数据库成为系统设计的一部分，而不是外部手工依赖。

### `main()` 在模拟什么完整流程

主程序不是简单演示几个 API，而是在模拟一个真实网关设备的工作周期：

1. 系统启动并打开数据库；
2. 注册 3 台设备；
3. 设置告警规则；
4. 模拟三批采样数据写入；
5. 对采样结果做告警检查；
6. 输出设备概览和告警历史；
7. 做完整性检查和旧数据清理；
8. 更新设备在线状态；
9. 系统结束并清理测试文件。

这就是为什么这章叫“实战”而不是“再讲一个语法点”。

### 为什么要用三台设备做不同数据分布

示例给三台设备设置了不同的温湿度分布：

1. 室内设备：温度在正常附近波动；
2. 室外设备：温度更低；
3. 车间设备：温度更高，更容易触发高温告警；

这样设计的好处是：

1. 更接近真实物理场景；
2. 让统计结果更有差异；
3. 让告警规则更容易被触发，便于演示；
4. 让设备概览表更有教学价值。

### `checkAndRecordAlerts()` 为什么很像规则引擎雏形

这个函数做的事情其实很有代表性：

1. 先查出当前设备启用的所有规则；
2. 对每条规则逐一判断是否触发；
3. 如果触发，就写入 `alert_events`；
4. 最后返回本次触发数量。

这已经具备了一个轻量规则引擎的基本形态。虽然还很简单，但它很好地展示了：

> 数据库不仅能存数据，还能承载一部分业务配置和业务决策流程。

### `printDeviceSummary()` 为什么是很典型的报表查询

这个函数把多张表信息压缩成一张概览表，里面同时包含：

1. 设备 ID、名称、状态；
2. 数据条数；
3. 平均温度、最高温度、最低温度；
4. 告警次数；

这类查询在真实项目中通常就是：

1. 后台首页概览；
2. 设备管理面板；
3. 运维监控报表；

所以它非常像“真实产品代码”里的 SQL，而不只是教学玩具。

### 维护逻辑为什么要放进类接口里

示例把 `integrityCheck()` 和 `cleanOldData()` 都做成了类方法，而不是主函数里散写 SQL。这样做的意义在于：

1. 运维动作和业务动作一样都是系统能力的一部分；
2. 后续你可以很自然地把它们接到定时任务、命令接口、远程维护入口里；
3. 这让“数据库维护”从临时手工操作变成了可编程的系统功能。

## 8.5 生产环境建议

### 文件系统注意事项

| 文件系统 | SQLite 兼容性 | 注意事项 |
|----------|--------------|---------|
| ext4     | ✅ 完全兼容   | 推荐 |
| FAT32    | △ 基本兼容    | 不支持完整文件锁语义，尽量单进程使用 |
| tmpfs    | ✅ 兼容       | 掉电数据丢失 |
| NFS      | ❌ 不推荐     | 锁机制不可靠 |

### 为什么文件系统会直接影响 SQLite 可靠性

SQLite 依赖：

1. 文件锁；
2. 日志文件；
3. 原子写入语义；
4. 正常的同步行为；

因此文件系统不是“底层透明细节”，而是数据库可靠性的直接前提。

特别是在嵌入式设备里，存储介质和文件系统的选择往往比桌面环境更敏感。

### 嵌入式部署清单

1. ✅ 使用 `WAL` 模式。
2. ✅ 设置 `synchronous = NORMAL` 或根据可靠性要求改为 `FULL`。
3. ✅ 设置合理的 `cache_size`。
4. ✅ 批量操作使用事务。
5. ✅ 定期清理旧数据。
6. ✅ 定期运行 `PRAGMA integrity_check`。
7. ✅ 实现数据库备份机制。
8. ✅ 使用参数绑定防止 SQL 注入。

### 生产环境还应额外考虑什么

如果真的要把本章示例演进成生产系统，通常还会继续补这些点：

1. 更严格的错误码和日志记录；
2. 异常掉电恢复策略；
3. 版本升级时的数据库迁移脚本；
4. 定时维护任务；
5. 告警去重、节流和通知通道；
6. 历史数据归档或上传云端；
7. 更细粒度的权限控制和输入校验。

这也是实战章节真正想传达的一点：

> 教程里的 demo 是一个可运行骨架，而不是生产系统的终点。

## 8.6 本章小结

- 嵌入式场景下 SQLite 应封装为模块化接口。
- 数据清理策略是长期运行设备的必要功能。
- `WAL` 模式 + `synchronous = NORMAL` 是嵌入式常见推荐配置。
- 告警系统可以通过触发器或应用层逻辑实现。
- 统计查询可用聚合和多表关联做概览输出。

### 把本章浓缩成一套心智模型

如果要把第八章压缩成最核心的几句话，可以记成：

1. 嵌入式数据库系统不是几条 SQL，而是一套长期运行的数据管理模块。
2. 表设计要围绕业务职责拆分：设备、采样、规则、事件分开管理。
3. 性能、可靠性、可维护性必须一起考虑，不能只顾“先跑起来”。
4. 数据清理、完整性检查、状态管理和告警记录都应该被设计成系统能力。
5. 真正的实战不是会写单条 SQL，而是能把数据库整合进完整业务流程。

## 教程总结

恭喜完成本教程。到这里，你已经不只是学会了几条 SQL，而是逐步建立了一整套 SQLite 学习路径：

1. **数据库基础**：理解表、行、列和关系型思维。
2. **SQLite 特性**：理解它为什么适合嵌入式、本地工具和轻量系统。
3. **CRUD 操作**：掌握创建、插入、查询、更新和删除。
4. **高级查询**：掌握 JOIN、子查询、索引、视图、HAVING、CASE。
5. **事务**：理解 ACID、提交、回滚、保存点和并发控制。
6. **C API 详解**：掌握 `prepare/bind/step/column/finalize`、BLOB、自定义函数、错误处理。
7. **性能优化**：理解事务、索引、PRAGMA、维护操作的性能与可靠性取舍。
8. **嵌入式实战**：把前面所有知识整合成一个可运行的数据采集管理系统。

如果你能把前八章的示例代码都真正看懂并自己改写一遍，那么你已经具备了在真实项目中使用 SQLite 的扎实基础。
